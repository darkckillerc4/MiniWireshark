# MiniWireshark V5.3.4: development plan

**Status:** PLAN ONLY. No production code has been changed. Coding starts only when the owner says so, and only after 5.2.3 is tagged.
**Base:** the final, tagged 5.2.3. While this plan was written, 5.2.3 was still in progress on branch `v5.2.3` (head `c4ddefc`, 67,235 lines). All line numbers below refer to that head and **will move**. Find the code by its symbol name, not by its line number.
**Theme:** eleven medium changes that make MiniWireshark easier to start, understand and trust, plus the largest bug campaign the project has run (fifteen sweeps). This is the biggest release since 5.0.
**Rules that hold throughout:** one production file (`miniwireshark.py`), no `.exe` shipped, defensive features only, no new dependencies, privacy defaults unchanged, no new outbound destinations, and every new string in English, French and Spanish.

---

## 1. Goals, non-goals and how success is measured

**Goals**

1. **Start fast on Windows.** A start from the Start-menu shortcut skips compiling the 3 MB file.
2. **One screen answers "am I ready?"** It covers capture driver, permissions, network card, data folder, history and privacy, with a fix button for every problem.
3. **More devices named correctly.** This uses evidence the app already collects but ignores, and accuracy is measured instead of assumed.
4. **"What changed?" reads like a story,** grouped by day, instead of a flat event list.
5. **The behaviour baseline knows the time of day.** It explains what it learned, ignores stale memory, and judges a TV and a laptop differently.
6. **Unusual activity is shown in one place,** with the worrying reading and the innocent reading side by side.
7. **Seven guided investigations instead of two.** Each one ends with "here is what to try" or "we can't tell from here".
8. **Call quality you can see.** Measure loss and jitter of video and voice calls from packet headers alone.
9. **Notice problems while the window is minimised,** with an opt-in Windows tray notification.
10. **Faster and lighter.** A profile-driven optimisation of the analysis hot path, memory and capture buffers.
11. **One-page "Network check-up" report,** redacted by default, that a beginner can print or send.
12. **Bug campaign.** Fifteen sweeps (§4) run before, during and after the features, and every finding is fixed or explicitly deferred with a reason.

**Non-goals:** a Windows `.exe`, winget, MSIX or code signing (single `.py` until 6.0), new protocol dissectors except RTP, RTCP and STUN headers for MC8 (and fixes that fuzzing finds), new connectors, machine learning or a local AI model, any online lookup or new outbound destination, active probing of other devices, raising the Python floor, splitting the file.

**Success measures (checked at M17)**

## 3. Courtroom, hearing A: design of each medium change

**How it was held:** this was a single-agent simulation. One Claude played advocate, prosecutor, architect, QA, release engineer and judge, and an independent prosecutor review was added afterwards (§3.8). The scores are judgment, not measurements.

**Scoring:** weights are benefit 25, feasibility 15, safety 25, performance 10, maintainability 15 and distribution 10. Each criterion gets a score of 0–5, and the weighted total is out of 100. A safety or distribution score of 0–1 is a veto. Doing nothing (the status quo) always scores well on safety, so the judge also requires real benefit.

### 3.1 MC1: fast start on Windows

| Option | Advocate | Prosecutor | Score |
|---|---|---|---|
| A. Status quo | No risk | Every start pays the full compile (≈ 2.5 s estimated on Windows, unmeasured) | 67 |
| **B. Start-menu and desktop shortcut that runs `pythonw -c <cached loader> <script>`** | Reuses `CACHED_RUN`, which is already tested. No file is shipped besides the `.py`. A stale or missing copy falls back to compiling | A `.lnk` caps its arguments (keep the command ≤ 1,000 characters). `CACHED_RUN` today reads the `.pyc` path only from `MW_PYC`, which a shortcut can't set. The time saving on Windows is unmeasured; the measured win on Linux is memory | **82** |
| C. Self-written `.pyw` launcher stub in the data folder (doc 07, option C) | Works when the `.py` is double-clicked | A second code file that must stay in step with the main one, and it still needs a shortcut to be found | 69 |
| D. Spawn a child from the `.pyc` | No new files | Two processes and more memory. The parent still compiled the file, so no time is saved | 62 |

**Verdict: B (82),** gated: build it only if 5.2.3 M0 measured ≥ 1.5 s of compile time on the owner's PC, or ≥ 100 MB of compiler memory left behind.
**Design details (from the prosecutor review):** the loader variant computes the `.pyc` path itself, the same way `compiled_copy_path()` does (per-user cache, keyed on the script path), and accepts no path from outside. After a shortcut start, the app calls `prepare_compiled_copy` as it does today, so the first start after an update compiles once and refreshes the copy for the next one. **Dissent (C):** a user who keeps double-clicking the `.py` gets no gain. The answer is that the readiness screen (MC2) offers the shortcut once.
**Safety condition (prosecutor):** the `.pyc` is code. It must live in the per-user cache folder (not a shared or archive folder). The loader checks magic, mtime and size (it already does), and `keep_compiled_copy` keeps writing it atomically. The elevated relaunch (`_relaunch_elevated`, which today passes the plain script) must **never** load the compiled copy. An elevated process loading a file that a standard process can write is a privilege-escalation path. A self-test pins this.
**Shortcut creation:** PowerShell `WScript.Shell` with `CREATE_NO_WINDOW`, so no new dependency. It is created only when the user clicks, never automatically, and removing it is one click.

### 3.3 MC3: device identification

| Option | Advocate | Prosecutor | Score |
|---|---|---|---|
| A. Keep adding `add()` rules by hand | Familiar | Unmeasured, and every rule is code. Rules contradict each other silently | 69 |
| **B. A declarative signature table plus a labelled synthetic corpus** | Data, not code. One engine scores it. Accuracy becomes a number a self-test enforces. Option 55 fingerprints finally get used | The table must stay small. Bad entries could mislabel many devices at once | **88** |
| C. Import an external fingerprint database or online API | Large coverage | Online lookup breaks privacy, and licence and size break single-file shipping | **51 (vetoed: safety 1, distribution 1)** |

**Verdict: B (88).**

- **Table:** `DEVICE_SIGNATURES`, inside the file, ≤ 40 KB of source. It maps DHCP option 55 lists, option 60 classes, mDNS service types and TXT `model=` patterns, SSDP device types, NetBIOS suffixes and OUI vendor groups to a kind, a weight and a plain-English reason. Hand-curated from public documentation and the owner's own devices (with consent); never copied from licensed databases.
- **Engine:** `classify_device` keeps its signature and output `(class, word, reasons)`, so callers don't change. The existing `add()` rules move into the table where they are pure data, and stay as code where they need logic (gateway, IPv6 router adverts, virtual adapters).
- **Real-capture rule (from the idea-pool court, IP-014, score 68):** every DHCP option 55/60 row must be backed by a real capture, because iOS and macOS, and Windows 10 and 11, share fingerprints. A row with no capture behind it doesn't ship. Option 55 matches never go above the "Possibly" level on their own. Fingerbank stays out (no free embedding, and its cloud API sends data out).
- **Corpus:** about 60 synthetic devices (phones, laptops, printers, TVs, consoles, cameras, IoT plugs, routers, VMs, randomized-MAC phones) built with the existing packet builder. A self-test computes accuracy and precision per kind, and fails below the §1 targets.
- **Option 55 plumbing:** `dhcp_params` is already stored on each device but cut to 80 characters in `parse_dhcp`. Keep the full list, in order, and normalise it before matching.
- **Randomized MACs:** first *measure* how often a rotating phone shows up as a new device in a demo scenario with rotation. Fix it only if it happens (merge on DHCP client ID or hostname, with the reason shown).
- **Removes** the dead `guess_device_type` (C-02).

### 3.5 MC5: behaviour baseline v2

| Option | Advocate | Prosecutor | Score |
|---|---|---|---|
| **A. Upgrade the statistics** | Explainable ("usually 2 MB a minute at night, now 60 MB"). Standard library only | Needs careful priors to avoid false alarms | **82** |
| B. Machine learning (for example an isolation forest) | Catches subtler patterns | Needs numpy or scikit-learn, opaque, can't explain itself in plain English | **46 (vetoed: distribution 0)** |
| C. Status quo | — | Cold start every session, and night and day are judged as one | 75 |

**Verdict: A (82).** Four upgrades:

1. **Day and night profiles.** Two EWMA sets per device, split by local hour, each with its own count. This needs new per-minute accumulation: the existing `hours` histogram only counts active minutes. A device never seen at night has no night profile, so its first night activity is judged by the kind prior with the full threshold, and gets its own plain reason ("first time active at night").
2. **Priors by kind** (from MC3). A new device starts from its kind's typical profile, so the "learning" period drops from 15 minutes to about 5 per profile. The full threshold applies until it has its own history. The absolute `FLOORS` (5 MB up, 40 destinations and so on) scale by kind, so a small camera can still raise an alert.
3. **Stale memory is ignored.** Baselines are already stored in the history `baselines` table. Version the JSON stored in its `data` column, and make `load_baselines` read `updated` so baselines older than 14 days are dropped. No schema change.
4. **Visible state.** Each device shows "Learning (9 of 15 min)" or "Knows this device (3 days)", plus what it learned, in words.

**Tests:** a synthetic week replayed through the builder must give 0 alerts on the normal scenarios and 3 of 3 on the planted ones (§1).

### 3.7 MC7: investigations library

| Option | Advocate | Prosecutor | Score |
|---|---|---|---|
| **A. Five new investigations on the existing hypothesis-board engine** | Same engine, same "never a verdict" rule, same planted-cause tests | Each one needs a blind-spot scenario, or it will overclaim | **86** |
| B. A generic rule engine where investigations are data | Fewer lines per investigation | A new engine to debug, and the wording gets generic | 71 |
| C. Status quo | — | Beginners' most common questions go unanswered | 72 |

**Verdict: A (86).** The new investigations:

1. **"Is my DNS working?"** Failure rate, slow answers, a DNS server change (from `change_digest`), and encrypted DNS seen.
2. **"Is IPv6 working?"** Router adverts, addresses, the share of traffic over v6, and a broken-v6 fallback pattern.
3. **"Why can't this device connect?"** The DHCP Discover/Offer/Request/Ack chain, ARP replies, and the gateway reachable or not.
4. **"Is it my Wi-Fi or the Internet?"** Handshake time to the gateway compared with handshake time to remote hosts (passive), plus the Wi-Fi link reading, which honestly says when Windows hides it (BF-002).
5. **"Why does my call stutter?"** Uses MC8.

Each is reachable from the command palette, the Health tab and MC2's fix buttons, and each has a planted-cause test and a blind-spot test.
**Passive only:** the existing `_tcp_rtt` and `_dns_rtt` helpers send traffic (through `outbound()`) and must not be used by any investigation. An `ast` self-test checks that no investigation function calls them.

### 3.8 MC8: call quality (IP-020)

| Option | Advocate | Prosecutor | Score |
|---|---|---|---|
| **A. Passive RTP and RTCP header decoding, admitted only after a STUN exchange on the same 5-tuple** | Loss from sequence gaps and jitter per RFC 3550. SRTP payload stays hidden, but its header is readable. STUN-first gating limits false detection | A new decoder is a fuzzing target (S4 covers it) | **83** |
| B. Guess call quality from UDP timing alone | No decoder | Can't tell loss from silence, so it would overclaim | 58 |
| C. Status quo | — | "My call is bad" is a top beginner complaint | 70 |

**Verdict: A (83).** **Shape:** a `CallTracker` object fed by the UDP flow updates, like `ProtocolTracker` in `DeepAnalyzer`. The stateless `_fast_udp` gets only a hook, so MC10 can still rework the hot path. **STUN-first rule:** a 5-tuple becomes a call candidate after a STUN binding on it, or after a STUN exchange between the same two hosts in the previous 60 s, which covers flows that begin mid-call. Calls that never send STUN (some apps do this) are not detected, and the card says "some call apps can't be measured" rather than guessing.
The output is a "Calls" card under Health: "Your video call lost 4% of packets between 20:01 and 20:03; jitter 38 ms (usually fine below 30)". It shows no names or content, the evidence level is Observed, and the card links to "Why does my call stutter?".

## 4. The bug campaign

"Heavily bug fix everything" is turned into fifteen sweeps, each with a method and an exit rule. Bug IDs continue from 5.2.3's B-01 to B-45 as **C-01 onward**.

| # | Sweep | Method | Exit rule |
|---|---|---|---|
| S1 | 5.2.3 carry-over | Compare B-01 to B-45 with the 5.2.3 final changelog | Every B-ID is either fixed in 5.2.3 or carried into C-IDs |
| S2 | Windows field evidence | Bugs from 5.2.3 M0/M9 on the owner's PC and any 5.2.x reports | All triaged, severity H and M fixed |
| S3 | GUI crawler | Re-run the 5.0.2 crawler (every tab, view, dialog and settings page × 3 languages × 2 themes × 4 text sizes × 1024×768 to 1920×1080), including the new MC2, MC4 and MC6 surfaces | 0 clipped, overlapping or unreadable widgets |
| S4 | Dissector fuzzing | Mutated frames from the packet builder through every dissector in the registry (bit flips, truncation, length-field lies, nested-length loops), with a fixed seed so runs repeat | 0 unhandled exceptions in ≥ 1,000,000 frames, no frame taking > 50 ms on Linux (Windows allowance set from M0 numbers) |
| S5 | Silent failures | Read every `except …: pass` block and `contextlib.suppress(Exception)` (C-04) and classify each as *keep* (with a reason in a comment), *log* (to the flight recorder) or *handle* | 0 silent passes in capture, history, update and outbound paths |
| S6 | Thread safety | List every `Thread` target and `JobRunner` job. Any Tk call outside the Tk thread, or any shared structure written from two threads without its lock, is a bug | All found fixed. Add a debug-mode guard that asserts the Tk thread in widget helpers |
| S7 | Soak | 8-hour replay of stress profile S2 at 2× speed, on Linux and on Windows (Remote Control) | Memory slope ≤ 5 MB/h after the first hour, no handle or thread growth, no freeze > 0.5 s |
| S8 | Static checks | pyflakes, plus a standard-library `ast` self-test for: text `open()` without encoding, Windows `subprocess` without `CREATE_NO_WINDOW`, `datetime.utcnow`, mutable defaults | pyflakes 0. The `ast` self-test passes and keeps passing |
| S9 | Translation integrity | Every string has EN/FR/ES parts, and the `{placeholders}` match in all three | Self-test passes. Wording corrections still wait for the owner's review sheet |
| S10 | Privacy and security review | `/security-review` on the 5.3.4 diff. The outbound ledger destination list must equal 5.2.3's | No new destination. Every finding fixed |
| S11 | Coverage | Run the self-tests under the standard library's `trace` module, with `threading.settrace` so worker and Tk-side threads count, and report executed lines per region. It is slow, so it runs as a separate long job, not in every milestone's test pass. **Baseline at M0**, comparison at M14. Untested regions get tests, starting with capture, history and outbound | Every region ≥ 60% at M14, and no region below its M0 number |
| S12 | Differential decoding | Decode the same frames two ways for existing protocols (fast wire decoder against `decode_packet`, the scapy path, which extends the existing comparison test) and compare the fields. For RTP and STUN, scapy is not a full oracle, so the MC8 numbers are compared with an independent reference computation written in the test (RFC 3550 Appendix A.8). Any disagreement is a bug in one of them | 0 unexplained disagreements on the builder corpus and on S4's mutated frames |

## 7. Test and budget policy

- Every C-ID gets a self-test named after it (`test_c01_keychain_secret_not_in_argv`). Every medium change gets at least one GUI test.
- The self-test count never falls.
- New `BENCH_LIMITS` entries: `story_build_7d` (≤ 150 ms Tk time), `ready_panel_fill` (≤ 50 ms of Tk time, with probes off-thread), `classify_device_corpus` (≤ 5 ms per device), `rtp_stream_update` (≤ 0.2 ms per packet), `checkup_render` (≤ 2 s, off-thread), and `history_90d_open` (≤ 2 s).
- Self-test count: at least +120 over 5.2.3 final (MC tests, C/BF/IP regression tests, S12–S15 scenarios).
- No real network data in the repository. The corpus and the scenarios are synthetic.

## 8. Risks

| Risk | Mitigation |
|---|---|
| 5.2.3 slips or changes the code this plan relies on | M0 re-checks §2 against the tagged 5.2.3 before any work starts |
| Signature table mislabels a whole class of devices | Corpus precision floor. Every label carries its reason. The user override always wins |
| Baseline v2 raises false alarms after a restart (loaded stale state) | New in M7: `load_baselines` drops rows older than 14 days (today `updated` is never read). Priors use the full threshold until the device has its own history |
| Versioned baseline JSON hurts older copies | No schema change. A 5.2.3 copy reading a 5.3.4 row is pinned by a self-test, and if it can't read the row it relearns that device |
| Shortcut command too long or blocked by antivirus | Measure the length in a self-test (≤ 1,000 characters). The feature switch can turn it off. Never auto-create |
| Elevated process loads a writable `.pyc` | The elevated path never uses the compiled copy, and a self-test pins it |
| The 67k-line file and long sessions burn tokens | One milestone per session. Search, then read only the region. Handoff note every session. No re-reading of finished milestones |
| Windows-only items can't be verified from the cloud | They stay "needs Windows evidence" until run under Remote Control |
